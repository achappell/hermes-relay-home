## Intent

**Problem:** After hermes-relay-home#83 the live Home acknowledged a tail `session.interrupt`, yet the next `prompt.submit` failed with `hermes_unavailable` and every later prompt on that bridge was refused. The Standard speak-stream sidecar answers `stop` by closing its socket without an `end` frame; the production audio adapter let `websockets.ConnectionClosed` escape the bridge's typed handling, so `_close_audio` never ran and `HomeBridge` kept the terminal turn active while the endpoint had released it.

**Approach:** Report a closed sidecar as `ConnectionError` at the adapter, as every other audio port implementation does. Treat a closure that follows Home's own stop request as the normal end of that turn's stream (`audio.frame` `end`, not a failure). Release only the turn that owns the sidecar. No sleeps, retries, reconnect workaround or diagnostics suppression; a close without a stop request stays a failed stream.

</frozen-after-approval>

## Implementation Notes

- Evidence (live Home b964082, Home-side records, content-free): interrupt acknowledged; audio phase recorded `protocol_error` at the same instant; the next `prompt.submit` rejected in 29 ms by `bridge.submit_prompt` (not the readiness gate) with `hermes_unavailable`. Grounded by source reading; reproduced locally below.
- `WebsocketsAudioSocket.send_json` / `receive` (`bridge/production.py`): `ConnectionClosed` becomes `ConnectionError`.
- `HomeBridge._stop_audio` marks the owning turn `audio_stop_requested`; `_next_audio` returns an `end` frame (`reason: stopped`) instead of raising when the sidecar closes after that mark. `_close_audio` keeps its existing owner check, so a late close from a finished turn cannot touch a newer turn.
- Tests, each red before the change: adapter test with a real `websockets` server that closes after `stop`; websocket-level endpoint test with that real sidecar (bridge kept `home-turn-1` active before; now the client gets `end`, never `unavailable`, the next prompt is admitted at once, and a repeated old-turn interrupt neither reaches Hermes nor stops the new turn's sidecar); bridge-level test that the stop-closure is a normal `end`, releases its own turn, and a late close with the old owner leaves the next turn and its sidecar untouched.
- Smoke (throwaway, not committed): real `hermes-home` process, paired credential and client claim, local fake Standard whose sidecar closes after `stop` with no `end` (0.2 s flush). With the fix 3/3: acknowledgement after 0.23 s, `audio.frame` `end` only, next prompt admitted as a new turn, no upstream `session.interrupt`, sidecar stops `[True, False]`. Against `b964082` the same smoke fails exactly as live: the next `prompt.submit` returns `hermes_unavailable`.
- Docs: stop-closure semantics added to `bridge-contract.md`. Changelog is generated by release-please from the conventional PR title.
- Not verified: the live sidecar's `stop` behavior beyond Home-side records, the live household Hermes, and any device. Needs deployment and a phone re-run.

## Review Triage Log

- Mapping `ConnectionClosed` only at the audio adapter, not the JSON gateway adapter: the gateway reader already has its own closed-socket handling and was not implicated by the evidence. Out of scope.
- Treating a stop-requested close as `end` could hide a sidecar that died for another reason right after a stop: acceptable; the user asked to stop and the stream is over either way, and a close without a stop request still reports a failed stream.
