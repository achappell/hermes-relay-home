topic: Standard Hermes compatibility and cross-surface migration
updated: 2026-09-13T21:04
---

- (direction) Slice 0 is the cross-surface Standard Hermes compatibility and migration foundation; it must be planned and gated before the remaining next-wave feature slices are sprinted.
- (decision) Home owns the cross-surface migration boundary and compatibility evidence; each surface repository owns its adapter, local configuration, lifecycle, presentation, and device validation.
- (decision) The migration preserves the surface-facing SessionProtocol and normalized event meanings wherever possible; transport, authentication, route, and server-boundary changes stay behind adapters.
- (decision) The target server path is the Standard Hermes Channel; no surface may require a fork-only event, fork-only assistant semantic, or fork-only server behavior to pass the migration gate.
- (decision) The existing fork path remains available during rollout as an explicit compatibility and rollback path, but no live turn may silently switch transports or replay across a route or transport change.
- (decision) The default transport changes only after every in-scope surface passes its conformance and live-smoke gate for text, response audio, interruption, reconnect, and honest failure.
- (decision) Home bridge adoption and direct-client migration are separate work packages: Home can terminate endpoint credentials and open Standard Hermes server-side, while direct TUI, phone, browser, Puck, and display adapters migrate independently.
- (decision) The migration must preserve existing Hermes JSON event names and ordering, binary little-endian response PCM, audio metadata, interrupt behavior, structured-prompt correlation, explicit commands when advertised, and cumulative text-preview replacement semantics.
- (decision) Audio/text synchronization is a migration gate, not a presentation assumption: a surface may claim synchronized words only when it has validated timing metadata or a verified playback-clock contract; arrival time is never authority.
- (decision) A missing optional timing feature produces an explicit compatibility or unavailable-timing state; it does not authorize a surface to guess word timing from network arrival.
- (capability) CAP-1: The project has one versioned Standard Hermes compatibility matrix that records each required capability, the stock-server evidence, the legacy-fork behavior, and the supported fallback.
- (capability) CAP-2: A fake Standard Hermes endpoint and Home bridge can prove the normalized session contract for hello, turn, text, response PCM, audio metadata, interruption, reconnect, prompts, and commands without a live network.
- (capability) CAP-3: Each in-scope surface can use the target boundary through its existing local session abstraction without duplicating Hermes wire parsing or changing answer authority.
- (capability) CAP-4: Each in-scope surface can migrate endpoint configuration and authorization from direct fork access or personal bearer credentials to the approved Home or Standard Hermes boundary without losing profile, history, or device identity.
- (capability) CAP-5: Each in-scope surface passes a surface-specific text, voice, interruption, reconnect, timing, and failure validation gate, with evidence recorded by its owning repository.
- (capability) CAP-6: The rollout can select an explicit compatible path, report its route and capability state, preserve a safe rollback path, and never change transport during an uncertain active turn.
- (capability) CAP-7: The project can remove fork-only dependencies from the default delivery path after the final gate without changing surface semantics or silently broadening credentials.
- (constraint) The migration cannot introduce a second household authority, shared transcript store, broker, or new Hermes channel merely to make the transition easier.
- (constraint) Home-issued endpoint credentials and Hermes bearer credentials remain distinct; personal Hermes tokens never move to displays, hardware, browsers, or ordinary diagnostics.
- (constraint) Migration compatibility does not mean feature parity by invention; unsupported prompts, timing, commands, attachments, or audio behavior must be typed and visible rather than emulated silently.
- (constraint) Legacy and Standard paths must be selected before a turn begins. Route or transport fallback after a turn may have reached Hermes is reconnect-only and requires fresh user initiation.
- (constraint) The migration plan must account for TUI, iOS, Android, ReSpeaker Puck, ESP32 Touch, W/K browser/iPad, Home bridge, and the Hermes server boundary; one surface's success never closes another surface.
- (non-goal) This slice does not rewrite Hermes, add a new Hermes WebSocket channel, or force all surfaces to use the same platform implementation.
- (non-goal) This slice does not finish pairing, Profile mapping, route roaming, diagnostics retention, Watch, notifications, typed choices, artifacts, or arbitrary files; it defines the compatibility gates those later slices consume.
- (assumption) The Standard Hermes voice-session protocol remains the preferred transport seed and can expose the required session, JSON, PCM, interruption, prompt, and optional timing behavior or an explicit capability absence.
- (assumption) The existing TUI SessionProtocol and sibling surface normalizers are stable enough to serve as migration seams rather than requiring a shared-core extraction first.
- (question) Which Standard Hermes release and endpoint shape are the supported migration baseline, and which capabilities are mandatory for the first default switch?
- (question) Does the Standard Hermes deployment provide authoritative speech timing for the required voice surfaces, or must the timing sidecar/playback-clock contract remain an approved compatibility dependency?
- (question) Which surfaces migrate directly to Home first, and which may temporarily remain direct Standard Hermes clients during the staged rollout?
- (question) What exact configuration conversion preserves existing profiles, local history, device identity, and safe rollback when a direct fork endpoint becomes a Home-paired endpoint?
- (question) What operational signal declares the migration gate passed and permits the legacy fork path to be retired?
