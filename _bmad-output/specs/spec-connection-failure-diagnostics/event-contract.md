# Event Contract

Proposed implementation detail for CAP-1–6; shared additions are not approved. Reuse `DiagnosticsRecorder` and its typed safe projection rather than introducing a parallel privacy policy. Existing schema-1 events/reports remain valid; explicitly version expanded schemas.

## Envelope and identity

Every operational diagnostic emitted by Home and the pilot proxy, including startup, cleanup and third-party transport warnings, has the following safe envelope. Unknown fields are rejected before serialization. No raw exception formatting, traceback locals, URI/request/header dump or arbitrary log message is an allowed fallback.

| Field | Contract |
| --- | --- |
| `schema` | New operational envelope integer `1`; distinct from existing event/report schema numbers. |
| `time_utc` | RFC3339 UTC with milliseconds and `Z`, captured at observation, not upload time. |
| `sequence`, `elapsed_ms` | Increasing per-process integer and monotonic elapsed time; durations use monotonic time. UTC is not proof of cross-host ordering when clocks differ. |
| `event_id`, `process_id` | Existing `evt-<32hex>` shape; new random `proc-<32hex>` per start. No host/user name. |
| `component`, `event` | Closed component set `home`, `proxy`, `ios`; event catalog below. |
| `build_ref` | Process ID referencing its startup provenance; retained files must carry a provenance header after rotation so a surviving event remains interpretable. |
| `connection_id`, `peer_connection_id` | Random `conn-<32hex>` per socket; optional peer/link ID only when explicitly negotiated. Reconnect creates a new ID. No endpoint, claim, Profile, device or session handle. |
| `home_connection_id` | Home-generated random `conn-<32hex>` socket ID disclosed by negotiated ready response; iOS retains it on pre-send events. Distinct from an iOS-local `connection_id`; client cannot select the Home ID. |
| `correlation_id`, `client_request_id` | Existing Home `corr-<32hex>` authority per explicit submission; optional random `req-<32hex>` client join token after negotiation. Never serialize arbitrary JSON-RPC `id`. |
| `correlation_state` | `local_only`, `linked`, `ambiguous`, `unavailable`; linked names an accepted scoped mapping, not proof of remote processing. |
| `leg` | `client_home`, `home_proxy`, `proxy_standard`, `process`. |
| `phase` | `startup`, `open`, `reconnect`, `submission`, `response`, `stream`, `closing`, `closed`, `shutdown`. |
| `outcome`, `failure_code` | Event-specific closed outcomes below; Home failure codes reuse its bounded registry (`stale_conversation`, `hermes_unavailable`, etc.), unknown maps to `unknown`. |
| `duration_ms`, `pending_count` | Nonnegative bounded integers; pending count saturates at 65535 and marks saturation. Request-specific records carry correlation rather than an unbounded pending-ID array. |

Allocate a Home correlation **before** readiness/refusal checks so a locally rejected request is also traceable; carry the same correlation into accepted turn events. Retain in-memory maps needed by existing pending work only until completion/close; retain the bounded safe association records below separately for delayed opted-in report lookup. Do not persist raw RPC IDs in logs. Existing route/turn fingerprints need not be expanded; new records omit private route names and identifiers.

Startup provenance contains allowlisted `app_version`, `build_number` where relevant, `source_revision`, `artifact_sha256`, `provenance_status` (`verified`, `unverified`, `unavailable`), and supported Standard baseline revision/version when known from approved deployment metadata. Emit actual loaded package/artifact identity, not merely checkout HEAD or a stale deployment file. Package version alone is insufficient; absent digest/commit stays absent with status unavailable. Record runtime and WebSocket library versions, UTC clock source (`system`) and configured ping/close numeric settings as observations only. Never include paths, command lines, environment, signing secrets or configuration dumps. Standard's own existing logs cannot be made comprehensive without agent changes: explicitly label its interior unknown; timestamp safe adapter observations at Home/proxy instead.

## Event catalog

Each row adds fields to the envelope; absent facts are `null`/`unknown`, not invented. Lifecycle transitions, not every text/audio frame, are logged. Healthy outcomes use the same shape as failures.

| Event | Required observation and fields |
| --- | --- |
| `process_started`, `process_stopping` | Provenance; stop initiator `local_operator`, `process_shutdown`, `unknown`. A crash may lack stop evidence. |
| `connection_opened`, `connection_ready` | Socket ID/leg; ready kind `open` or `reconnect`; local readiness only, not model health. Reconnect links old connection when locally known. |
| `request_observed` | Correlation, connection, `operation=prompt_submit`, `trigger=explicit`, phase submission. This is not proof of upstream acceptance. |
| `upstream_submit_started`, `upstream_submit_outcome` | Correlation and upstream connection; `accepted`, `unavailable`, `rejected`, `interrupted`, `unknown`; failure code and bounded exception category. Accepted means supported submit response, not completed generation/audio. |
| `rejection_generated` | Correlation; safe failure code; `origin=readiness_gate`, `upstream_submit`, `authorization`, `validation`; whether unavailable latch was already set. |
| `response_write_started`, `response_write_outcome` | Correlation; `response_kind=accepted` or `rejection`; outcome `write_returned`, `failed`, `cancelled`, `skipped_closed`, `unknown`; phase and failure category. `write_returned` means local API returned only, **never client received**. Cancellation is not silently successful. |
| `transport_observed`, `connection_closed` | Leg, connection, initiator, pending count, classification and numeric close facts below; request-specific `request_transport_lost` per pending correlation. Both proxy pumps report source/target IDs; first observed terminal event and counterpart close request are separate events. |
| `request_transport_lost` | Correlation; pending state `awaiting_write`, `awaiting_response`, `response_resolved`, `stream_active`, `none`, `unknown`; local observed outcome only. |
| `recovery_observed` | Connection ready plus previous connection/correlation when known; `next_explicit_correlation_id` is recorded only when user submits, otherwise absent. The next request's ordinary outcome proves acceptance/failure; a later `turn_terminal` distinguishes actual completion/interruption/unavailability. Never generate a probe prompt. |
| `turn_terminal` | Existing turn correlation; `completed`, `failed`, `interrupted`, `unavailable`; `text_state` and `audio_state` each `completed`, `unavailable`, `not_requested`, `unknown`. Do not infer what the user heard. |
| `client_response_received`, `client_request_resolved` | Follow-up only: record at real receive/decode and pending-continuation resolution respectively; correlation/token when known, `response_kind`, safe failure code, pending state and existing uncertainty flag. A received frame is not a decoded rejection until resolution. |
| `diagnostics_loss` | Cumulative `queue_dropped`, `schema_rejected`, `sink_failed`, `rotation_evicted`, `correlation_conflicts`, each saturating unsigned integer; sink state `ok`, `degraded`, `unavailable`. Emit on recovery/rotation/start as available; preserve existing diagnostics-status visibility. |

## Close and failure classification

Close fields: `initiator=local|peer|unknown`, `close_trigger=operator|shutdown|counterpart_closed|keepalive|transport_error|unknown`, `classification`, `sent_close_code`, `received_close_code`, `close_order=sent_first|received_first|simultaneous_or_unknown`, `exception_category`, `cause_category`. Codes are integer 1000–4999 or null; local sentinel/no-frame values (e.g. 1006) must be labeled `observed_status_code`, never claimed as a sent/received frame. Raw reason text is always omitted. Allowlisted exception categories: `connection_closed_ok`, `connection_closed_error`, `timeout`, `os_error`, `cancelled`, `protocol_error`, `other`, `none`; nested causes map through the same bounded categories, never arbitrary class names or messages.

| Classification | Evidence requirement |
| --- | --- |
| `submit_unavailable` | Actual submit exception or local unavailable latch; record which, do not imply process crash/model outage. |
| `keepalive_pong_timeout` | Library-supported structured observation that pong wait expired; warning text alone is insufficient. Record observed phase independently. |
| `normal_shutdown` | Normal close frame/known local shutdown, without interpreting successful request completion. |
| `timeout_during_close` | Timeout observed while closing; retain any normal 1000 sent/received codes and observed keepalive trigger separately. Do not relabel as 1011/pong timeout just because logger says keepalive. |
| `transport_error`, `unknown` | Other bounded observations; no causal assertion without supporting fields. |

If both pong expiry and closing timeout are actually observed, emit separate sequenced observations; terminal classification describes closing timeout, not a speculative initiating root cause. Use a library logging adapter that extracts safe structured state/exception types and public close facts; do not monkeypatch the library, parse arbitrary traceback prose for causality, suppress the warning, or tune timeouts. Where the library exposes no fact, emit unknown.

## Shared metadata and mixed versions

**Proposed Home/proxy contract:** Home generates a random connection link ID for each proxy socket, sent only on that configured hop in handshake header `X-Hermes-Diagnostic-Connection`. Proxy strictly accepts `conn-` plus 32 lowercase hex characters, logs the safe link beside both locally generated leg IDs, and does not forward the header to Standard. Invalid/missing diagnostic metadata is ignored/count-only and never affects authorization or connection success. Home's pending correlation→socket map joins submissions to that proxy connection; proxy remains a transparent byte relay and does not parse/log message content. Concurrent requests remain distinct at Home; proxy close evidence applies to the connection, not a fabricated per-request Standard result. Direct Standard connections send no diagnostic header.

**Proposed Home/iOS contract:** after explicit upgraded-client socket opt-in below, advertise optional capability `diagnostics_correlation_v1` on the existing Home ready result. Only then may a request carry `diagnostics.request_id` (`req-<32hex>`); results/errors optionally return `diagnostics.request_id` and Home `diagnostics.correlation_id` at the envelope location defined below. This metadata is diagnostic only, not authentication, deduplication or retry state. Legacy clients send unchanged RPCs and receive no added fields: their current decoders reject unknown envelope and nested capability keys. No metadata enters the Standard request. Omit all additions unless the client opted in; no silent compatibility break.

### Proposed exact wire shape

Use optional **top-level JSON-RPC envelope** `diagnostics`, alongside `jsonrpc`, `schema`, `id`, `method`/`result`/`error`; never insert it into method `params`, `result` payload or `error.data`. Home's `_require_param_shape` is strict, while `_parse_request` currently reads only ordinary envelope keys. Implementation must explicitly parse/validate the new object before dispatch and retain it through success/error serialization; the legacy RPC ID still resolves the request and is never a diagnostic identifier.

An upgraded iOS client whose decoder supports these fields sets handshake header `X-Hermes-Diagnostics-Version: 1` on its authenticated HomeBridge WebSocket. Home accepts only the literal `1`, remembers this opt-in per socket, and does not forward/log the header. Missing/invalid header means the exact legacy ready/response shape; old Home ignores the optional header and advertises nothing. This header is feature negotiation, not authority. Swift currently rejects unknown top-level envelope keys (`handleTextFrame`) and nested capability keys (`HomeWireCapabilities` / `HomeCoding.requireExactKeys`); update those explicit allowlists before a client sends the header. On an opted-in socket only, ready `result.capabilities` adds `diagnostics_correlation_v1: true` (Boolean) and `client_diagnostic_report_schemas: [1, 2]` (unique integer array, allowed values 1 and 2). Home synthesizes these from its own installed support, not Standard capabilities; add them explicitly after `_safe_capabilities` sanitization, including reconnect. Absence/false means no correlation extension; absence of schema advertisement means schema 1 only. An opted-in client may use schema 2 only for the Home whose authenticated ready result advertised it; clear cached support when that Home connection is replaced/invalidated and fall back to schema 1 until re-advertised. Do not open/reconnect a conversation merely to upload diagnostics. Whenever schema-2 support is not currently established (including background upload without an active ready binding or an older Home), a safe schema-1 projection may be uploaded with only original schema-1 fields/event names, retaining original event times and never fabricating provenance; new-only event types are omitted. The schema-2 source remains bounded/local until support returns or expiry, and the existing upload scheduling/rate limits remain unchanged. Each immutable projected report gets its own report ID distinct from its schema-2 source so a later schema-2 snapshot cannot conflict with per-device report-ID deduplication. Persist that projection ID, exact serialized bytes and retry/completion state with the source snapshot: retries reuse the same ID/bytes, successful upload is recorded, and retaining the schema-2 source never creates a fresh projection ID on another flush. Projection and source share the existing per-Home queue budget; this adds no extra queue slots or faster upload cadence.

The following are **metadata-only JSON projections**, not full conversation requests/responses or log records; ordinary required fields/payloads remain unchanged and are deliberately not shown:

```json
{"result":{"capabilities":{"diagnostics_correlation_v1":true,"client_diagnostic_report_schemas":[1,2]}},"diagnostics":{"version":1,"home_connection_id":"conn-33333333333333333333333333333333"}}
{"method":"prompt.submit","diagnostics":{"version":1,"request_id":"req-11111111111111111111111111111111"}}
{"result":{},"diagnostics":{"version":1,"request_id":"req-11111111111111111111111111111111","correlation_id":"corr-22222222222222222222222222222222"}}
{"error":{"data":{"code":"stale_conversation","delivery":"known"}},"diagnostics":{"version":1,"request_id":"req-11111111111111111111111111111111","correlation_id":"corr-22222222222222222222222222222222"}}
```

Request object has exactly `version` (integer 1, not Boolean) and `request_id` (string matching the token shape); submission response object has exactly those plus Home-generated `correlation_id`. A ready/reconnect response instead has exactly `version` (integer1) and `home_connection_id` (Home-generated `conn-<32hex>`). Home obtains the socket ID implicitly from its endpoint, never from a client-supplied request value. Emit submission response metadata only for a valid negotiated request token; negotiated ready/reconnect metadata needs no request token and is available before submission. An invalid/oversized/unknown-key diagnostic object is ignored and counted, without changing the normal RPC result. A malformed ordinary RPC retains existing errors and may have no correlation. No capability is an authorization grant.

Client request tokens and proxy link headers remain **untrusted join hints**. Home generates its own socket ID and request correlation independently. Request-token uniqueness is scoped to that Home socket: repeated tokens or conflicting request mappings mark `correlation_state=ambiguous`, omit authoritative cross-peer mapping and increment a safe conflict counter without suppressing/changing requests. Cap live token tracking at4096 entries/socket; if exhausted, mark further links unavailable rather than evicting into false uniqueness. Clear live pending maps at close; the bounded retained association below handles delayed reports. The proxy header remains bound to its particular authenticated Home-facing socket; duplicate active link IDs are ambiguous, not global authority. Never join by token alone or time proximity. Schema-2 uploaded assertions remain client-reported and cannot overwrite Home observations; duplicate event IDs with conflicting content are rejected/count-only, not merged as fact.

**Client platforms:** the envelope `platform` is `ios`, `macos` or `android`; `platform` selects the `model` vocabulary and nothing else in schema 1 or 2 depends on it (see `spec-home-client-diagnostics.md` § Android platform). Android sends the same bounded content-free events and the same correlation fields; optional identifier fields are omitted, never `null`.

**Report evolution:** schema 1 is closed and unchanged. Propose schema 2 retaining its required top-level report metadata and limits, extending typed events with `event_id`, `sequence`, `connection_id`, `home_connection_id`, `request_id`, `correlation_id`, `correlation_state`, `leg`, `pending_state`, numeric close fields and received/resolved event names from this contract. Reuse existing `time`, `name`, `phase`, `code`, `uncertain`, `duration_ms`, `launch_id`; report-assembly app/build metadata describes assembly only, not the source build of all persisted events. Apply strict ID/enum validation and reject unknown fields; do not convert arbitrary strings to permitted IDs. Home first accepts both versions and review tooling renders missing correlation as unavailable. iOS emits schema 2 only after explicit advertised report support; otherwise sends unchanged schema 1 and marks unavailable evidence locally. Report support advertisement is part of the same owner approval gate. Schema 2 additionally requires top-level `origins` (array, ≤100 entries within the existing64KiB total). Each immutable origin has exactly `launch_id` (existing UUID), `app_version`, `build_number`, `os_version` (existing bounded sanitized formats), `source_revision` (40/64 lowercase hex or null), `artifact_sha256` (64 lowercase hex or null), and `provenance_status` (`verified`, `unverified`, `unavailable`). Capture these at launch/event generation; every event's existing `launch_id` resolves to exactly one origin. For retained legacy events whose source version was not captured, nullable source metadata and unavailable status are mandatory: never backfill today's version. Event IDs and source sequence stay stable across snapshots, queue persistence and uploads. Origins travel with their referenced events and are discarded only when no retained event needs them. Current report-level app/build/OS remain assembly metadata; upload receipt time remains separate. No claim that assembly, upload and generating builds match. Retain existing per-Home opt-in and authenticated report route; no new upload path, receipt RPC, export UI or automatic content capture.

### Delayed report association (proposed; same shared approval gate)

Home's ready handshake already precedes prompt submission. On the explicitly opted-in socket, its ready/reconnect envelope exposes `diagnostics.home_connection_id` as shown above; an upgraded iOS client records that Home-assigned ID before declaring the binding ready. The client then captures `(home_connection_id, request_id)` on each pre-send schema-2 event, so loss of the submission response does not erase the join. Home generates a fresh random128-bit socket ID at socket creation, never deliberately reuses it across sockets/processes, and does not accept a client-selected replacement. Reconnect on the same physical socket keeps the ID; reconnect on a new socket obtains a new ID from that socket's ready response. The client clears the old binding when the socket changes and does not copy the old Home ID into new-socket events. Missing negotiated metadata means correlation unavailable, not a fabricated ID or a conversation failure.

Use the existing protected Home SQLite diagnostics/report authority, not a new collector: retain `(authenticated Device FK, Home connection_id, request_id) → (Home correlation_id, process_id, observed_at, expires_at, state)` when a request is observed, before attempting its response. Home obtains Device identity from its established authentication and connection ID from the actual socket, never either from submitted diagnostic metadata. A request that never reaches Home has no association and stays unavailable. Device FK is the existing internal authorization/storage identity, **never emitted in operational logs or supplied by client report fields**. Logging remains nonblocking/fail-open; an association whose queued write is lost is missing evidence, not proof of delivery.

Proposed bounds: **1,024 association rows/device and4,096 total**, expire no later than seven days after original observation, no retention extension on upload/read, oldest eviction with loss accounting. Rows survive ordinary socket close and Home process restart. Duplicate tokens on one Home socket mark their retained association ambiguous; different Home-assigned sockets may use the same token without being merged. Once a socket's live token cap is exceeded, do not create more associations for it; a late repeat cannot be promoted to unique after token-state eviction. These diagnostic bounds do not increase existing event/report quotas.

Delayed report lookup filters by the **authenticated uploading Device FK and exact Home-assigned socket ID plus request token** before returning a Home correlation. A spoofed token or Home socket ID from another device cannot match the victim's private Device scope; report-provided correlation IDs never override lookup. Missing, evicted, expired or corrupt association rows yield unavailable; conflicting rows yield ambiguous. Do not fall back to timestamps, global tokens or same-device tokens without the exact Home socket ID. New sockets cannot accidentally inherit a deliberately recycled ID; therefore missing old rows need no caller-scope ledger, tombstones, global seven-day disable guard or dirty-journal machinery. A unique association proves Home observed that request, not that a client truthfully received its response. Show the bounded mapping/loss outcome in the existing authorized review path; introduce no new public route or private identifier in emitted logs.

### Deterministic report packing

The 64 KiB limit is **65,536 serialized UTF-8 bytes for the entire HTTP JSON body**, including report metadata, `origins`, event IDs and escaping—not merely event count or pre-encoding string lengths. Sender uses one deterministic serializer (UTF-8, no pretty-print whitespace, stable key order) and retains the resulting immutable bytes for retry. Take eligible events in source observation order (origin plus sequence, using persisted snapshot order across origins); greedily append whole events and their previously absent origin entries while both 100-event and 65,536-byte bounds hold. Emit only origins referenced by packed events. When the next otherwise-valid event does not fit the current report, seal that report and continue in the next available existing queue slot. Preserve event IDs, original times/sequences and origin mappings; never truncate an event/string/origin into validity or rewrite its generating provenance. Do not reorder into a false cross-process time sequence.

Before queueing, size-check the complete encoded report again. If an event plus its required origin and minimal report metadata cannot fit alone, drop that event and increment the existing bounded diagnostic-loss accounting; if fixed metadata itself cannot fit, drop the candidate report and record a schema/size loss. Do not send an oversized candidate or retry it forever. Additional packed reports consume the existing ≤10 snapshots/Home budget and existing upload scheduling/rate limit; if there is no slot, apply the existing bounded queue eviction/drop behavior and count evidence loss, rather than allocating an overflow queue. Pending/schema-1-projected/source state shares that budget. Server continues enforcing its independent strict 64 KiB bound; a permanent size/schema rejection is a terminal diagnostic upload failure with loss accounting, not a retry loop. Transient transport retries retain the same report ID and bytes under existing bounded policy.

## Bounded storage and failure defaults (proposed)

- Home typed recorder remains default 4096 events with ≤14-day expiry and existing drop accounting; SQLite timeline and operational sink use the same redacted facts. Do not weaken existing schema validation.
- Home/proxy local JSONL: 2 KiB maximum serialized record, nonblocking 1024-record queue, drop newest on full queue, active 10 MiB + four rotated backups (50 MiB maximum per process), expire files/records at 14 days. Rotate before exceeding size; write a safe provenance header into each file; validate bounds without truncating into malformed JSON. Restricted service-owner write and authorized-operator read; no public serving or upload by default.
- Replace unbounded runner redirection of these operational diagnostics with one rotating owner. No second unbounded stdout/stderr copy or unsafe library fallback. Remove existing private claim-handle prefixes and raw `exc_info`/exception formatting from affected diagnostic paths, retaining typed warnings/errors rather than suppressing them.
- Drop invalid/oversized records, not arbitrary fields guessed safe. Queue/sink/permission/disk errors cannot escape into request handling. Nonblocking cumulative loss counters remain in existing diagnostic status where available; a safe rate-limited fallback health record (at most once/minute) uses the same schema, never raw errors. If every sink fails, evidence may be absent: counters are observable while process lives and emitted on recovery, not falsely promised durable across a crash.
- Shutdown drains for at most 100 ms without delaying the live request/close path; unresolved diagnostics count as loss. Crashes may leave a partial final line; readers ignore only that incomplete line and label a gap. Do not claim complete evidence after rotation/loss.
- Automatic iOS report storage remains separate: existing 64 KiB/100 events, 7-day retention, 30-second per-device receipt rate limit, 100/device and 1000 total retained report caps. iOS retains its bounded 100-event context, ≤10 queued snapshots/Home and existing 4 MiB persisted-file read bound. Existing opt-in, renewal/revocation and deletion behavior remain unchanged. Canonical 30-day metrics and 7-day approved incident bundles are not introduced or changed here.
