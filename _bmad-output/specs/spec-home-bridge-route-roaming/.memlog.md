topic: Home Bridge and Route Roaming
goal: Route paired endpoints to one Household Server through approved network paths while preserving the ordinary Hermes voice-session protocol and no-replay behavior
slug: home-bridge-route-roaming
updated: 2026-09-13T21:20
---

- (direction) Headless express mode: distill the canonical Home next-wave PRD, Home architecture spine, existing v1 contracts, and Hermes voice-session README into one narrow bridge and route-roaming contract; do not invent an HTTP or identity mechanism that the sources leave open.
- (decision) Slice C owns the endpoint-to-one-Household-Server route and bridge boundary; Slice A owns endpoint credentials, Slice B owns mapping and conversation claims, and Slice D owns diagnostics storage and incident capture.
- (capability) CAP-1: A paired endpoint selects the highest-priority currently reachable Approved Route to the one Household Server and shows which route it is using.
- (capability) CAP-2: A paired endpoint verifies that an approved route reaches the same Household Server before it uses the route for Home or Hermes work.
- (capability) CAP-3: Home can open an authorized conversation through the ordinary Hermes voice-session channel behind the bridge without exposing a Hermes bearer token to the endpoint.
- (capability) CAP-4: The bridge preserves the existing Hermes session messages, binary response PCM, timing metadata, and structured-prompt correlation across the endpoint/Home/Hermes path.
- (capability) CAP-5: A paired endpoint can recover from an approved-route loss without automatically resending a turn whose delivery may be uncertain, then accept a fresh user turn after honest readiness returns.
- (capability) CAP-6: The endpoint can distinguish route, Home-bridge, authorization, and Hermes-session readiness or failure without inventing a second session authority.
- (decision) Approved route priority is fixed for the first slice: home network first, Tailscale second, and public internet only when explicitly configured. The endpoint reports the active route and never attempts an unapproved public route.
- (decision) All approved routes identify the same logical Household Server. Route labels, URLs, and credentials do not themselves prove household identity; the final proof mechanism remains an open implementation question.
- (decision) Home terminates the endpoint authorization boundary and opens the ordinary Hermes WebSocket with a server-held Hermes token. The endpoint receives an opaque conversation handle and existing Hermes events, never the personal Hermes bearer token.
- (decision) The bridge preserves protocol meaning rather than translating it into a Home-specific assistant dialect. Existing JSON events, binary little-endian PCM, audio metadata, timing records, interrupts, and structured prompts remain the transport seed.
- (decision) Route recovery may establish a fresh transport for the same Home and Hermes session identity, but it never automatically resubmits an uncertain turn or replays the old response. A fresh prompt requires fresh user initiation after readiness.
- (decision) Live microphone capture and speech-to-text remain endpoint responsibilities. Binary microphone ingress is not added to the Hermes v1 bridge; response PCM travels back through the existing voice-session stream.
- (constraint) The one Household Server remains the sole household authority; route roaming must not create a second household configuration, credential authority, Profile router, or Hermes session authority.
- (constraint) A route is eligible only when it is explicitly approved and proves the same Household Server identity. Public internet access is opt-in and is never an implicit fallback.
- (constraint) Endpoint Home credentials and the server-held Hermes bearer credential are distinct. Neither credential appears in route labels, session payloads, snapshots, logs, diagnostics, transcripts, or audio.
- (constraint) The bridge accepts an already authorized opaque conversation handle from the Home claim flow. The endpoint cannot supply an arbitrary Profile ID, Hermes session identity, prompt, transcript, or audio to widen authorization.
- (constraint) No new Hermes WebSocket channel, fork-only wire event, assistant semantic, or endpoint-specific Hermes dialect is introduced for roaming or pairing.
- (constraint) The bridge must preserve event ordering, response PCM bytes, audio metadata, timing offsets, and prompt IDs when the existing channel provides them. Missing optional timing remains an honest compatibility condition, not permission to guess from network arrival.
- (constraint) A route or transport failure is visible and fail-closed. Home does not promote another endpoint, switch Profiles, replay an uncertain turn, or silently create a second Session to repair the failure.
- (constraint) Connection and route status must remain distinct from turn delivery status. A reconnect can become ready without claiming that an interrupted or uncertain turn succeeded.
- (constraint) Domain route policy and bridge authorization remain testable through injected route, identity, clock, credential, and WebSocket ports without a live public network or Hermes endpoint.
- (non-goal) This slice does not define the final same-Household identity proof, route-discovery protocol, or public reverse-proxy/TLS deployment.
- (non-goal) This slice does not implement pairing or credential issuance, Profile mappings and wake arbitration, Watch/notifications, diagnostics retention, or artifact behavior.
- (non-goal) This slice does not add binary microphone ingress, a new Hermes channel, server-side speech recognition, or a second assistant protocol.
- (non-goal) This slice does not replay an old response, resolve uncertain delivery automatically, or provide multiple household servers for one endpoint.
- (assumption) Slice A issues the endpoint an opaque limited Home credential and Slice B returns a ready/unavailable result plus an opaque conversation handle before endpoint capture begins.
- (assumption) The standard Hermes voice-session v1 channel remains available at the server boundary and supports hello, turn, interrupt, ping, JSON events, binary response PCM, and the documented optional speech_timing event.
- (assumption) The endpoint can retain its logical Home and Hermes session identifiers across a transport reconnect, subject to the standard channel's session and cursor rules.
- (question) What exact cryptographic or challenge-based proof establishes that local, Tailscale, and optional public routes are the same Household Server?
- (question) Where are Approved Routes configured and refreshed, and how does an endpoint learn an approved route list without treating a stale list as authority?
- (question) What exact versioned Home bridge envelope and endpoint WebSocket path carry device authentication, conversation handles, route status, and safe errors?
- (question) When a route changes during active response audio, should the endpoint drain local playback, stop it immediately, or expose a distinct interrupted state before reconnecting?
- (question) How should Home retain or re-establish the Hermes session identity and last-turn cursor across a route reconnect when the old transport ended during an active turn?
- (question) Which health and liveness probes belong to this bridge slice versus the later single-device health slice, and what probe budget is safe without opening a microphone or speaker?
- (event) Slice C contract seed recorded. Open questions are limited to identity proof, route configuration, exact bridge envelope/path, active-audio transition, session-cursor recovery, and health-probe ownership.
- (constraint) The endpoint may carry the ordinary channel's session fields, but it cannot choose an arbitrary Profile or Hermes Session identity to widen authorization; Home maps the opaque conversation handle to trusted server-side context and may overwrite untrusted identity fields.
- (constraint) The bridge preserves the standard channel's optional explicit command capability and cumulative text-preview replacement semantics when advertised; it does not turn commands into model input or print cumulative previews as separate messages.
